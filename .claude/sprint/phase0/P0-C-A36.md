## 0. Headline

A-3.6 is **not** "delete one body and fix up N readers". It is a one-body deletion that
**simultaneously widens five structurally different subjects**, only one of which — `IE` —
is what DICT §8 I5 licenses. I5's own 🚨 boundary clause
(`docs/spec/DICT-SEMANTICS.md:2025-2029`, DERIVED) states verbatim that I5 *"does NOT extend
that price to NAMES"* and that its subject is `match(IE, C τ̄)`. Four of the five readers are
name/data-scoping tables, not instance candidacy.

Two of those four carry a **measured acceptance NARROWING** that `typecheck.mdk`'s own prose
says §5 R2 cannot license (R2's two exceptions are both WIDENINGS), and one carries a
**live silent-wrongness regression** that the ratchet's own instruction — *"hand every row the
FINAL accumulator"* — creates rather than avoids.

**Ruling: A-3.6 cannot be implemented as written without an owner adjudication.** §1.3 is the
decision point. §4 cuts the bites that are safe under either ruling.

### 1.3 🚨 THE DECISION POINT — one body, five subjects

`typecheck.mdk` asserts the one-predicate invariant in eight places and the ratchet in three
more. The invariant is real and was earned. But its *justification* — that A-3.6 is a single
spec'd semantics change — holds only for `IE`.

`docs/spec/DICT-SEMANTICS.md:1939-1948` (I5, DERIVED): *"For a goal `C τ̄` … `match(IE, C τ̄)`
ranges over every instance declared in every module … Import scoping decides which **names** a
module may write. It never decides which instances exist."*
And at 2025-2029: *"🚨 I5 does NOT extend that price to NAMES … I5's subject is
`match(IE, C τ̄)`, and its closing sentence … is a **boundary clause** bounding I5's own claim
to instances — not a rule about how a predicate over names is scoped."*

The alias table, the ctor overlay pool, the field-owner multimap and the param-kind table are
**name-scoping tables**. Deleting one body applies an instance-candidacy licence to all four.

**Two candidate rulings, for the owner / architecture companion:**

- **(A) Literal.** Delete `declEnvVisibleAt`'s body; all five subjects go graph-global.
  Requires the field-owner narrowing (§2.1) and the alias widening (§2.3) to be separately
  licensed, since §5 R2's two enumerated exceptions are both *widenings* and one of these is a
  *narrowing*.
- **(B) Split (P0-C's recommendation).** Keep `declEnvVisibleAt` as the ordinal predicate for
  the name/data axis; introduce `ieCandidacyVisibleAt` (or flip at `ieSnapAt` alone) for the
  instance axis. Cost: the one-predicate invariant becomes a two-predicate invariant, and every
  comment that says "one body" must be re-cut. Benefit: A-3.6 delivers exactly I5, and the
  four name-scoping widenings become their own later units with their own fixtures.
  `CE` is genuinely ambiguous between the two (I4 is identity, not candidacy) and should be
  ruled explicitly rather than defaulted.

**This is not improvisable by an implementer.** It is the run's top escalation.

## 2. Per-reader risk — what actually moves, and whether it is safe

### 2.1 🚨 `declEnvSeedChain`, OWNERS half — the ratchet's own instruction is a live regression

**RELAYED instruction** (`test/registry_keying_ratchet.sh:201` and `:235`): *"What A-3.6 DOES
edit here is the chain's prefix sharing … hand every row the FINAL accumulator"*, and *"the
own-row exclusion is STRUCTURAL (the `omInsert` precedes the fold) … there is no ordinal test to
find, and A-3.6 does not disturb it."*

**DERIVED: those two sentences contradict each other, and the second is false under the first.**

`declEnvSeedChain` (`typecheck.mdk:3054-3062`) stamps row `m`'s id with `kacc`/`oacc` **before**
folding `m` in, so reader `k`'s seed = rows strictly earlier than `k`. The FINAL accumulator is
the fold over **all** rows, including `k`'s own. Handing every row the final accumulator
therefore **destroys the own-row exclusion** — the very thing the same row calls structural and
mandatory.

Consequence, DERIVED end to end:

1. Seed for module `k` now contains `k`'s own public records' owner keys.
   (`declEnvSeedChain:3060` → `declEnvRowVisible (m.demOrd+1) m` → non-own arm → `demPubDecls`
   → `declEnvVariantFieldOwners` → `addFieldOwners cn …` where `cn` is the `Variant`
   constructor name.)
2. `registerAllData … prog0` then registers `k`'s own decls again via
   `registerNamedFieldVariants` (`12784-12788`) → `registerRecordInfoKeyed o cname …`
   (`12495-12505`) → `addFieldOwners key=cname …`. **Same key, same `Decl` node.**
3. `addFieldOwners` (`12510-12513`) conses without dedupe.
4. `mangledHeadCandidates` (`9344-9349`) reads `fieldOwnersRef` **RAW** (no `sortUniqS`;
   contrast `fieldOwnerNames` at `8990-8992`, which does). A doubled key turns
   `lookupRecordByMangledHead`'s singleton gate from `Some pair` into the give-up arm.

`typecheck.mdk:2956-2964` and `24916-24934` document this exact hazard. The pre-existing
`appendDataUniverse` doubling is *inert only because nothing reads the multimap between it and
the next `resetState`* (`24928-24932`, DERIVED). **The seed doubling is not inert** — it is
present from before inference starts, i.e. across every record-field resolution in the module.

**Separately**, even with the own row correctly excluded, the owners seed going graph-global
means a **PUBLIC record in a topologically later, unrelated module votes in
`resolveFieldByOwners`' ambiguity test** → `T-AMBIGUOUS-FIELD` on a program that compiles
today. `typecheck.mdk:2902-2908` states this is MEASURED, and states its own verdict:
*"That is a silent acceptance NARROWING — false rejects on legal programs — and §5 R2's two
enumerated exceptions are both WIDENINGS carried by a could-not-pass-before fixture. A
narrowing cannot meet that bar."*

**Verdict: the owners seed must NOT go graph-global in A-3.6.** Under ruling (B) it does not.
Under ruling (A) it needs its own owner licence, and the correct shape is
"whole graph **minus own row**" (bite C-2), not the final accumulator.

### 2.2 `declEnvSeedChain`, KINDS half — moves judgments, quietly

`dataParamKindsRef` is read via `lookupTab`, first-match over identity-bearing `TabKey`s
(`typecheck.mdk:3018-3033`, DERIVED). Duplicate keys are *equal values* because

### 2.3 `aliasVisibleTo` — the alias NAME table goes graph-global

Under A-3.6, `aliasVisibleTo` (`3557-3560`) reduces to `ad.adPub && ad.adOrd != cur &&
not ad.adAttrib`. Conditions 2 and 3 survive **as written** (they are separate `&&` terms, not
part of `declEnvVisibleTo`) — DERIVED, and this half of the ratchet's constraint is correct.

What moves: a public `type` alias declared in a topologically later module enters every earlier
module's `aliasTableRef`. `aliasTableRef` is consulted by `fromAstTypeE` for **bare type names**.
So a module writing `Foo` in type position, with no import path to the declaring module, can now
resolve `Foo` to a foreign alias. This is precisely the *name*-scoping widening I5's boundary
clause disclaims. It is also cheap to make loud or leave silent depending on collision handling,
which nobody has looked at.

Mitigating fact, DERIVED (`3543-3545`): `deAliases` is small — 11 type aliases in the whole
tree — so blast radius today is near zero and perf is immaterial. That is a statement about
*this* tree, not about user programs.

**`could move:` any bare type-name resolution in a multi-module project. OWED: a fixture where
two unrelated modules declare the same public alias name.**

### 2.4 `declEnvRowVisible` → the ctor overlay pool — the safest reader

`overlayScanRows` (`26320-26327`) walks `deModules` in ordinal order and calls
`declEnvRowVisible cur m`, which returns `[]` for an invisible row. Every candidate is
**FIRST-wins** and the walk **early-exits** on the deciding candidate (`overlayDecided`,
`26333-26338`). Rows above `cur` are appended at the *end* of the existing scan order.

**Therefore the flip can only turn a MISS into a HIT** — it cannot change an existing winner.
DERIVED from the fold direction plus first-wins, not from a run. That makes this reader a
pure widening, monotone, and the one reader that is clearly safe in the R2 sense.

Caveat: `importedCtorTypeDecls`' result also feeds `seedCheckRun` (`26732`), the exhaustiveness
oracle. Extra `DData` decls there can **remove** a spurious "non-exhaustive" warning — a
diagnostic-only change that **no value golden can see** (this run's characteristic blindness).
