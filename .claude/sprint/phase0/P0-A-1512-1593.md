## 4. 🚨 THE RULING — the central question of this unit

> **Q (from #1512's body, restated by the brief): is retiring the elaborated trio onto a
> syntactic K possible, and if so how?**
>
> **A: Not onto a syntactic K. And the reason on record is not the binding one.**

### 4a. The recorded reason (perf) is real but NOT decisive, and it is UNMEASURED

The recorded rationale is `typecheck.mdk`'s `#154 PR-A` block, quoted in both #1512 and #1593:
re-registering every earlier module's public data per module *was* "the dominant remaining
O(N²)". **That is history, not a measurement of today's tree** — #1593 itself labels it
*"INFERRED, not measured"*. It is also weaker than it reads, because the overlay layer already
does a per-module re-registration out of K (§3): the shape is present, only the *breadth*
differs. **This does not settle the question in either direction, and nobody has run it.** OWED.

### 4b. The reason in the source is FACTUALLY WRONG on today's tree — and it will cost a round

`typecheck.mdk:3249-3260` ("WHY NOT JUST CALL `registerAllData`…") — the block #1519's CE header
at `:4254` explicitly forwards implementers to — says elaboration

> MINTS FRESH TYVAR IDS (`mintParamReprs` → `freshVars`) from a **global monotonic counter**.
> `buildDeclEnvs` runs in the driver PREAMBLE, before the per-module walk that owns that counter

**DERIVED false.** `tyvarCounter` is a **`PerRun`** field (`typecheck.mdk:6346`), initialised
`Ref 0` by `freshPerRun` (`:6441`), and `resetState` (`:6526-6529`) mints a **whole fresh
`PerRun` per module**. So the counter is **per-module**, not global-monotonic. Consequences:

- Schemes in `universeDataEnv` **already** cross module boundaries carrying ids minted under a
  *different counter epoch*, and this is already tolerated — every consumer re-instantiates
  through `freshSubst` (`:7073-7075`) / `instantiateRecord` (`:12526`), so a `Scheme`'s
  quantified ids are scheme-local.
- The in-source claim "would still shift every later tyvar id and move every scheme this PR must
  NOT move" was an argument against **A-3.2a's byte-identical bar**. #1593's bar is explicitly
  *not* byte-identical (#1111: "semantics, not byte-identical"). **That argument does not
  transfer.**

The same wrong claim is repeated in the `CE` block header at `typecheck.mdk:4250`
("mints fresh tyvar ids off the global counter"). #1512's own 2026-08-12 adjudication caught
this ("the tyvar counter is **per-run, not global**") — **but the correction never reached the
source.** An implementer starting from `grep 'WHY NOT JUST CALL'` — the documented entry point —
gets the falsified version. See bite **P0A-D2**.

### 4c. The binding reason is DIAGNOSTICS, and it is not written down anywhere

Elaboration **emits type errors**: `fromAstTypeE` pushes `T-ALIAS-ARITY` (`:7532`) and
`T-ROW-KIND-MISMATCH` (`:7563`). Both go through `pushTypeErrorOnce` /
`pushTypeErrorOnceAt` (`:6090`, `:6104`), whose dedupe (`Once`) is scoped to
`perRun.typeErrors` — a field of the bundle `resetState` re-mints **per module**.

Therefore, moving elaboration into `buildDeclEnvs` (preamble, one pass over the whole graph):

1. **merges the dedupe scope across the entire module graph.** A shape that today produces one
   diagnostic *per importing module* would produce **one for the whole compile**. That is
   strictly **fewer** diagnostics on a program that is rejected today.
2. **relocates the diagnostic out of any module's harvest window.** The preamble runs before
   the core pass; `checkModulesPreamble` snapshots per-module diagnostics downstream of it.
   A preamble-time push has no module to be attributed to.

Both are **loud → silent** transitions. AGENTS.md's own corollary: *"A fix that makes a defect
QUIETER is a severity INCREASE."* And this sprint's exit criteria name a silently widened
acceptance as *the* characteristic failure the gate suite is blind to.

**This is the argument that forecloses preamble-time elaboration, and it is on neither issue.**
It is also *cheaper to check* than the perf question: it needs no build, only the four sites
above.
