## 2. THE RULING — does #1438's bare-spelling leg make coherence-over-IE wrong?

**This is the sharpest question in the unit. RULING: NO — provided coherence reads
`ieRows` and never the three index buckets. Under that discipline the bare leg is
structurally unreachable, and coherence over IE is STRICTLY MORE CORRECT than coherence today.**

Derivation, four steps, all **DERIVED** from `:3867-3911` and `:4031-4038`:

1. `ImplEnv` (`:3872`) has a **population** field and **index** fields:
   `ieRows : List ImplRow` is the population in build order; `ieConcrete`, `ieHeadless`,
   `ieIfaceTags`, `ieUnivSnaps` are the index.
2. The two-key mint is applied **only to the index**. `ieInsertRow` (`:4031-4033`) reads:
   `ieInsertRowKeys (oblIfaceKeys ir) r { env | ieRows = env.ieRows ++ [r] }` — the record
   update that appends to `ieRows` takes **no key**; only `ieInsertRowKeys`/`ieInsertRowAt`
   consume `oblIfaceKeys`, and `oblIfaceKeys` (`:20642-20645`) is the two-key function
   (identity key + `TkBare NsIface irName`).
3. Therefore a sweep iterating `ieRows` sees each impl **exactly once** and consults **no
   bucket key**. #1438's collapse cannot reach it.
4. The interface comparison then becomes a **predicate over the payload `IfaceRef`**, not a
   key lookup — which is what makes the correct acceptance-direction rule expressible at all
   (§2b). A key-based grouping has no way to say "absence makes no claim".

### 2a. 🚨 The contrapositive is the trap, and it is the obvious optimization

`cohScan` is O(pairs). A reviewer or implementer will notice that `ieConcrete`/`ieHeadless`
already group impls by `(interface, head)` and propose iterating buckets instead of pairs.
**That is the bug.** Each row is indexed under BOTH keys, so a bucket walk sees every row twice,
and in the **bare** bucket it compares impls of two *different* interfaces that merely share a
spelling — reproducing today's false reject (§3, probe B) inside the new substrate, plus
double-reporting every pair. The IE block's own doctest asserts this bucket collapse is live and
deliberate: `listLen (mregLookupK ieProbeBareKey ieProbeEnv.ieConcrete)` is **2**, with the
comment *"If this ever reads `1`, the leg was dropped and #1438's pin must have flipped with
it"* (`:4162-4170`). **Every bite that touches the projection must carry a comment forbidding a
bucket walk.**

### 2b. The comparison predicate: `sameTyConHead`, not `ifaceIdMatches`

**DERIVED.** Two identity-comparison rules exist in this tree and they are exact inverses:

- `sameTyConHead n1 o1 n2 o2 = n1 == n2 && not (tyConIdsConflict o1 o2)`
  (`compiler/frontend/ast.mdk:496-506`) — name equality, and an **absent origin makes no
  claim** (matches anything).
- `ifaceIdMatches a b = a != "" && a == b` (`compiler/frontend/ast.mdk:137-138`) — **absence
  never matches, not even itself.**

`recordCandIsType`'s header states which to use when (`:9189-9195`): *"`sameTyConHead` lets an
ABSENT origin match anything, because it answers an **ACCEPTANCE** question where a false reject
refuses a valid program. [`recordCandIsType`] answers a **LOOKUP**, where a false hit is silent
wrongness — so absence must never match."*

**Coherence is an acceptance question.** So `sameTyConHead` is the correct rule, and it is also
the **fail-loud** direction here: an impl whose `implOrigin` is `OriginUnresolved` still
compares by name, so no live rejection can silently vanish. `ifaceIdMatches` in this position
would turn every unstamped-origin conflict into a silent accept — a severity increase.

**Note also:** coherence's HEAD half already routes through `sameTyConHead` (`cohGoR` `:15049`,
A-2.10). This unit proposes **no** re-keying of the head, so the #1317 T1 rule / closed S0
#1277 are untouched. ✓

### 2c. Consequence: A-3.7 partially drains #1438's coherence reach

`TYPECHECK-TARGET-ARCHITECTURE.md:2134-2136` §10.6 "Not settled here": *"**Coherence still keys
