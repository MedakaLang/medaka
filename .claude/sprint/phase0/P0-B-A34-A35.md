## 5. Findings that change the sprint's scope or Phase 2's ordering

### 5.1 🚩 A-3.5a as cut here does NOT read IE — so it may be an A-3a unit (OWNER RULING OWED)

**RELAYED claim, from `test/registry_keying_ratchet.sh`'s `declEnvsRef` row:** *"A-3.5a
(`universeIfaceRequiredRef`) and A-3.5b remain owed; both read IE and stay in the A-3b lane."*
#1557's §6 table says the same in more detail: *"impl completeness relocates onto CE-required ×
`IE.ieMethods` at the reading ordinal."*

**DERIVED, and it contradicts that:** the "× IE" half is optional, and taking it costs a
**diagnostic location**.

- The diagnostic's location comes from `firstImplMethodLoc methods` (`:15519`, `:15594`,
  `:15530-15532`) — the first impl-method **body**'s `exprLoc`.
- `ImplRow` carries **no `Loc`**, deliberately and with a derived reason: `DImpl` has no location at
  all, so an `Option Loc` there could only ever be `None` (`:3847-3854`).
- Therefore **iterating `IE.ieRows` loses every `T-INCOMPLETE-IMPL` location**, which moves every
  diagnostic golden containing one — for no gain: the `defined` set from `ieMethods` is by
  construction `map implMethodNameTc methods` of the same decl (`implDeclFact` `:3972-3979`), i.e.
  the very list `map implMethodName methods` computes at `:15518`/`:15593`, and IE's rows owned by
  `cur` are the same impls `prog` already iterates.

So the honest options are:

- **(A) recommended — keep iterating decls, read `required` from CE.** Preserves the location; makes
  A-3.5a **CE-only**; leaves `ieMethods` with no consumer (bite `A5a-6`).
- **(B) iterate `IE.ieRows`.** Requires first giving `ImplRow` a location derived from a method
  body's `Expr` — which `:3852-3854` explicitly calls *"its own unit"* — and then still moves
  goldens if that derivation is not byte-identical to `firstImplMethodLoc`.

**Why this reaches the orchestrator and not just the implementer:** RULING 2's overturn condition,
as the owner applied it to A-3.5c on 2026-08-12, is *mechanical*: a part **genuinely independent of
IE** splits out as an A-3a unit. Under option (A), A-3.5a meets that condition exactly as A-3.5c
did — and the mechanical test the owner wrote for A-3.5c transposes verbatim: *A-3.5a qualifies as
A-3a only if it keeps iterating `prog` rather than `IE.ieRows`.* If it is A-3a-eligible, **A-3.5a
does not sit behind A-3.4 in Phase 2's serial chain.** A-3.4 is done, so nothing is *blocked* either
way; what changes is whether Phase 2's A-3b lane is `3.5a → 3.5b → 3.6 → 3.7` or
`3.5b → 3.6 → 3.7` with 3.5a landable in parallel with the A-3a tail (#1512/#1593, Phase 1).
