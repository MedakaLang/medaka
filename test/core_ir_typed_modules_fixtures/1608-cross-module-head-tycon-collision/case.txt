CASE: cross-module interface method, two impls sharing one head tycon
OWNS:  nothing — no open issue. #1608 (the issue this case was built for) was
       CLOSED 2026-08-15 as mis-scoped at filing; the finding below is why. The
       untyped arms' answer is PINNED (main_perm*.untyped.txt), not ledgered.

── HOW THE EXPECTED VALUE WAS ESTABLISHED ────────────────────────────────────

NOT captured. Derived from the language semantics BEFORE any arm was run, then
compared:

  `bi : Box Int` and `bs : Box String` are both given explicit, unambiguous type
  signatures, so no defaulting or inference freedom is in play. Method selection
  is by the receiver's TYPE (docs/spec/DICT-SEMANTICS.md; the "most specific
  wins" ruling). `Box Int` matches `impl Tagged (Box Int)` and nothing else;
  `Box String` matches `impl Tagged (Box String)` and nothing else. Neither impl
  is more specific than the other — they are disjoint — so there is no
  overlap-resolution question.

  ⇒ `tag bi ++ " " ++ tag bs`  ==  "boxint boxstr", in BOTH permutations.

The two `import` lines that differ between main_permA.mdk and main_permB.mdk are
BARE imports. A bare import binds no names at all (AGENTS.md); its only effect is
to bring the module's impls into scope for dispatch. Reordering two of them
therefore changes no program meaning, and any arm whose answer moves is wrong
about something other than this program.

── WHY THIS SHAPE ────────────────────────────────────────────────────────────

Both impls have head tycon `Box`, so the argument's constructor TAG is `Box` in
both cases. An arg-tag dispatcher ("first impl whose tag matches wins") CANNOT
discriminate here even in principle; only a stamped route can. That makes this
the shape that separates a route-consuming dispatcher from a tag-guessing one —
and it is why the control case (distinct head tycons) is not a substitute.

── MEASURED, 2026-08-15, on a cold `make medaka` of this branch ──────────────

  arm                                        permA              permB
  ─────────────────────────────────────────  ─────────────────  ─────────────────
  eval, TYPED   (`medaka run`)               boxint boxstr ✅   boxint boxstr ✅
  native        (`medaka build` + exec)      boxint boxstr ✅   boxint boxstr ✅
  ceval, TYPED  (core_ir_typed_modules_main) boxint boxstr ✅   boxint boxstr ✅
  eval, UNTYPED (eval_modules_main)          boxint boxint ❌   boxstr boxstr ❌
  ceval, UNTYPED(core_ir_modules_main)       boxint boxint ❌   boxstr boxstr ❌

🚨 THE FINDING, and it re-scopes #1608: the two UNTYPED module drivers are
BYTE-IDENTICAL to each other in both permutations. #1608 was filed as a defect
SPECIFIC to `cevalModules` (compiler/ir/core_ir_eval.mdk) on the strength of a
table comparing `eval` ✅ against `core_ir_eval` ❌ — but that `eval` reading came
from `medaka run`, which is the TYPED path, while the `core_ir_eval` reading came
from core_ir_modules_main, which is the UNTYPED one. Same-arm, the two parallel
module drivers AGREE. There is no lockstep divergence between them on this shape.

What actually reproduces is the documented untyped arg-tag fallback, which
`evalModules` and `cevalModules` share by design (see cevalModules' own header:
"UNTYPED path, like cevalProgram / evalModules"). The ledger row for this case
pins that shared untyped value; the gate's LOCKSTEP check is what would catch a
future fix to one driver that is not mirrored in the other.

── DISPOSITION (2026-08-15) ──────────────────────────────────────────────────

#1608 was CLOSED as mis-scoped at filing, after the reading above was re-measured
on the reporter's ORIGINAL program (see 1608-original-literal-receiver/case.txt,
which recovers it verbatim from the sprint packet and reaches the same verdict).

The ledger rows this case carried were removed with it, and NOT because a fix
landed — the untyped arms still print the value below. A ledger row asserts "that
is a live defect, and here is the OPEN issue that owns it"; the first clause is
still true, the second is not. The behaviour is the untyped drivers' documented
arg-tag design, so it is now PINNED per entry in main_permA.untyped.txt /
main_permB.untyped.txt, graded byte-exactly by the gate's tier 3. Any movement,
including the arm becoming CORRECT, is red. The grading did not weaken — it got
stricter, since both entries are pinned where both were previously ledgered and
the pin needs no issue to stay honest.

── RE-DERIVED 2026-09-02: THE PIN MOVED, AND IT MOVED FROM A VALUE TO A REFUSAL ──

WHAT CHANGED, AND WHY IT IS NOT A BUMP. Sprint `argtag-decidability` (#2445)
gave the interpreter the eval-side twin of `emitArgTagRoute`'s native guard:
`checkArgTagDecidable` (`compiler/eval/eval.mdk`) REFUSES an arg-tag dispatch
whose surviving candidates are two impls OF ONE INTERFACE with distinct
canonical keys and no later dispatching slot — precisely "the runtime tag was
asked a question it cannot answer". This case's untyped arms are exactly that
shape, so they no longer print a value:

  MEASURED 2026-09-02, both untyped drivers, byte-identical to each other:
    :0:0: runtime error [E-AMBIGUOUS-DISPATCH]: arg-tag dispatch on a receiver
    of type 'Box' is undecidable: more than one impl is declared at that type
    head and the runtime tag cannot choose between them
  exit 1, stdout EMPTY. The tier-2 lockstep between `evalModules` and
  `cevalModules` is intact — both refuse, at the same point.

DECISION: A DELIBERATE IMPROVEMENT, and the pin is re-derived to match. The
value these arms used to print was, in this file's own words, "the coin landing
the right way, not the arm being right" — a first-impl-wins pick that depends on
import order and not on the program. Trading a silent coin flip for a loud,
coded refusal is the direction AGENTS.md's [W-QUIETER] names (loud→silent is a
regression; silent→loud is not), and it is the whole point of #2445. The pin
therefore stays a PIN — no ledger row, because there is still no OPEN issue and
nothing here to fix — and now records the refusal.

⚠️ WHAT THE RE-DERIVED PIN COSTS, STATED RATHER THAN GLOSSED. Tier 3 grades
STDOUT ONLY (`2>/dev/null`, exit code unread), so a refusal pins as the EMPTY
STRING. That is a WEAKER pin than the one it replaces: it reds if the arm starts
printing something again, but it cannot tell E-AMBIGUOUS-DISPATCH from any other
way of producing no output — a different panic, a crash, an early exit. The
information needed to make it strong again (the diagnostic code, the exit
status) is observable and simply not captured by this gate's tier 3. Making tier
3 grade `<exit>|<stdout>` and, for a refusal, the diagnostic CODE, is the fix;
it is a change to `test/diff_compiler_core_ir_typed_modules.sh` and was out of
the licensed scope of the fix packet that re-derived this pin (#2445 F-2, which
was licensed to `compiler/eval/eval.mdk`). Whoever next touches this gate should
do it — until then, read an `ok` on this entry as "still not printing a value",
not as "still refusing for the right reason".

WHAT DID NOT MOVE: the TYPED arms (tier 1) are untouched and still print the
hand-derived value on all three of `medaka run`, `medaka build`+exec, and the
typed Core-IR driver. Those are the shipping arms, and they are what makes this
entry's green fail-capable; the untyped arms never were a supported mode.
