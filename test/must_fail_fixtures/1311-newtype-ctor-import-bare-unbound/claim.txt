issue: 1311
what: `nmod.mdk` declares `export newtype NT = Wrap Int`. A `newtype`'s constructor
what: is UNCONDITIONALLY module-private BY DESIGN -- `public` is a parse error on
what: `newtype`, so there is genuinely no spelling that exports it (verified:
what: `public newtype NT = Wrap Int` -> parse error, exit 1). `main.mdk` imports
what: `NT(..)` (a wildcard that resolve happily expands to `[NT, Wrap]` regardless
what: of privacy) and uses `Wrap`.
what: Correct behaviour per the design: refuse the import member with a diagnostic
what: naming the rule (module-private constructor) and the remedy (or the fact
what: there is none). Observed: a bare `T-UNBOUND: Unbound variable: Wrap` at the
what: USE site (main.mdk line 10), with ZERO diagnostics on nmod.mdk and no
what: mention of the import anywhere. Contrast: the analogous abstract-`data`
what: case (`export data AT = MkAT Int`, no `public`) is refused at RESOLVE, ON
what: THE IMPORT MEMBER, with a message naming the rule AND a remedy
what: (`R-NO-EXPORTED-CTORS`: "'AT' exports no constructors ... Remove `(..)` or
what: export with `public export`"). The newtype case gets neither -- and per the
what: issue, the abstract-data message's own remedy would be ACTIVELY WRONG advice
what: for a newtype (there is no `public export newtype`), which is exactly what
what: makes silence worse than usual here.
what: MECHANISM (from the issue): resolve ACCEPTS the constructor at every step
what: (`expCtorsDirect`/`expTypeCtorsDirect`, gated on `newtypePub`, which `export
what: newtype` DOES set; `expandMemberNames` expands `NT(..)` to `[NT, Wrap]`;
what: `realImport` puts `Wrap` into `iaCtors`) -- so resolve has nothing to
what: complain about. `types.typecheck.publicDataDecls` disagrees: it has NO
what: `DNewtype` arm at all, so `Wrap` never reaches the public data universe, and
what: the mismatch surfaces two stages later as a nameless unbound variable.
what: This is a DIAGNOSTIC-CONTENT-AND-LOCATION defect (S2: misleading), not a
what: silent wrong-answer -- the program correctly fails to compile either way.
what: Pinning it here asserts TODAY'S unhelpful shape (wrong stage, wrong
what: location, no rule, no remedy) so the row flips the day the diagnostic
what: improves, at which point issue #1311 can be closed.
