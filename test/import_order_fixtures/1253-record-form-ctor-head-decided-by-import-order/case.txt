entry: main.mdk
what: #1253 (S0) an ambiguous RECORD-form ctor head resolves by import order, silently

`MkT { fx = 1 }` names a record-form constructor declared, identically, by BOTH `ra`
and `rb`. `recCreateHead` never consults the ctor-ambiguity set the POSITIONAL form
routes through, so no `R-AMBIGUOUS-CTOR` fires and the winner is whichever clause the
resolver reached last. Which `impl Tag` runs is therefore decided by import order,
at exit 0, with no diagnostic on any verb.

Observed by hand on a binary cold-bootstrapped from `main` @ 0af30a78, 2026-08-05,
before this gate existed:

    check, both orders          -> exit 0, `main : Unit`, NO diagnostic
    run,   ra clause first      -> FROM-RB
    run,   rb clause first      -> FROM-RA
    build, ra clause first      -> FROM-RA
    build, rb clause first      -> FROM-RB

⚠️ The `build` rows are NOT in #1253's issue body, which records `run` only. The two
engines pick OPPOSITE winners for the same source, so this is also a run-vs-build
disagreement at exit 0 on top of the order dependence. Both are graded here; both are
covered by the same ledger row, because both are the same unkeyed lookup.

DRAINED 2026-08-05 by #1319 unit 1 (#1111 A-2.11). The fix is in `resolve.mdk`, not
in the keying: `recPatHead` and `recCreateHead` now consult the CONSTRUCTOR ambiguity
peer (`ambiguousCtorErrors`) as well as the type one, so the record-form head reaches
the same `R-AMBIGUOUS-CTOR` its positional twin always did. The provenance-based
ambiguity TRIGGER itself is untouched — it is deliberately one rule across all four
namespaces — this only stops two occurrence positions from silently skipping it.

⚠️ WHAT THIS CASE NOW PINS IS A REJECTION, and that is the correct answer, not a
convenience: the program brings TWO different `MkT`s into scope and names one. Note
the drain moves it from "exit 0, order-dependent winner" to "exit 1 in every
ordering" — loud, not quieter.

⚠️ BUT "TWO DIFFERENT `MkT`s" IS THIS CASE, NOT THE WHOLE OF THE NEW REJECTION, AND A
READER MUST NOT GENERALISE FROM IT. The set the record head now consults
(`ctorAmbiguousSet`) counts PROVENANCES — distinct directly-imported modules — not
declarations. So ONE declaration reached by TWO import paths counts as two, and a
record head naming it is now rejected where it was accepted before:

    import pa_def.{Box, MkBox}      -- pa_re is `export import pa_def.{MkBox}`
    import pa_re.{MkBox}
    ... MkBox { bx = 3 } ...        -> Ambiguous constructor: 'MkBox' is brought into
                                       scope by both `pa_def` and `pa_re`, exit 1
                                       (baseline accepted this and printed `3`)

There is no silent wrongness in that shape to have been fixed — both paths name the
same declaration — so it is a genuine new rejection of a valid program. It is graded
S3 and deliberately NOT special-cased here, because the trigger is PRE-EXISTING and
deliberately ONE RULE across the value / type / interface / ctor namespaces: the
POSITIONAL spelling of that same program is rejected identically on the baseline
binary, and resolve's own note says a change to that rule must change all four
namespaces at once. This fix only stopped two occurrence POSITIONS from skipping the
rule; it did not touch the rule. Found in adversarial review of PR #1352, recorded
here so the next reader does not mistake it for a defect introduced by the drain.

(The diagnostic's fix advice — "drop the other's `(..)`" — is inapplicable to that
shape, since neither import uses `(..)`. Pre-existing message defect, ws:diagnostics.)

THIS CASE IS NOW THE REGRESSION GUARD, unledgered so the gate demands invariance.
Current behaviour, every ordering:
    check=1;codes=R-AMBIGUOUS-CTOR;schemes=;run=1:;build=1/-:
