what: #1326 REGRESSION GUARD — a same-named constrained binding elsewhere in the import
      graph must not decide whether an unrelated call site typechecks, in EITHER clause order

`qsmod.h : a -> a` and `psmod.h : Display a => a -> String` are two unrelated top-level
bindings that happen to share a bare name. The entry imports `qsmod.{h}` and calls
`tag (h NoDisp)`, which needs no `Display` at all; `psmod` is never named by the entry —
it arrives only because `midmod` imports it. `NoDisp` deliberately has no `Display` impl,
so if `psmod`'s obligation is ever attributed to `qsmod`'s `h`, the program is rejected.

⚠️ THIS IS THE "feature + UNRELATED code still behaves" SHAPE. The assertion is about
`tag (h NoDisp)` — a call site that touches none of the machinery under test. A fixture
that only exercised `viaP 5` would pass on the broken compiler.

WHY THIS CORPUS RATHER THAN A GOLDEN. #1326 was an IMPORT-CLAUSE-ORDER defect and neither
the issue nor its must-fail pin said so: the poisoning happened only in the
constrained-then-unconstrained module processing order, which follows import-clause order,
so the LAST-processed same-named module was the victim. With `midmod` first the entry was
rejected; with `qsmod` first it checked clean. A golden records one ordering and then
defends it. Permutation invariance is the property that was actually violated.

HOW THE EXPECTED VALUE WAS ESTABLISHED — derived, not captured. `h` here is unambiguously
`qsmod`'s identity function (`psmod`'s is not in scope in the entry under any spelling), so
`tag (h NoDisp)` is `tag NoDisp` = "ok"; `viaP 5` interpolates `5` at `Display Int` = "5".
The program must print `ok / 5` at exit 0 in EVERY ordering. Confirmed on a binary built
from the #1337 fix branch; confirmed to FAIL (check exit 1, `No impl of Display for NoDisp`
with the caret on `h`) in the midmod-first ordering on a binary built from `main` @
b5f8c489, so this row can fail and did.
